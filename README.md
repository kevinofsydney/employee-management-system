# Courant Translator Roster

A small, mobile-friendly roster and timesheet app for translators. Translators sign up with email, wait for one of two admins to activate them, see their shifts, and submit actual hours and expenses. Admins roster shifts, review hours, spot missing timesheets, and export approved work for MYOB Business.

## What it does

- Roster shifts in 15-minute steps, including shifts that cross midnight.
- Prefill each timesheet with rostered times. Translators can correct and resubmit until approval.
- Record paid time with no break deduction. Split actual hours at Sydney midnight so only Sunday hours use the Sunday payroll category.
- Record multiple expenses per shift, each with a date, short description, amount, and “receipt sent to David or an admin” confirmation. Receipts are not uploaded.
- Show unsubmitted shifts in the admin dashboard from 9am Sydney time the morning after the shift ends.
- Show approved lifetime hours by translator, with Standard and Sunday totals.
- Export an approved-hours CSV, a separate approved-expenses CSV, and a tab-delimited MYOB Business timesheet import file.

The application stores names, email addresses, rosters, worked hours, and expense records. It does not store tax file numbers, bank details, employee contracts, or receipt files.

## Local setup

All dependencies are installed inside this repository. No global npm package installation is needed.

1. Install dependencies: `npm install --cache .npm-cache`.
2. Create a Clerk application with email sign-up and email verification. Copy `.env.example` to `.env` and set its publishable key.
3. Copy `.dev.vars.example` to `.dev.vars`. Add the Clerk secret key and PEM JWT public key from the Clerk dashboard. Set `ADMIN_EMAILS` to the **two exact email addresses** allowed to administer the app. Keep these files out of Git.
4. Apply the local database migration: `npm run db:migrate:local`.
5. Start locally: `npm run dev`.
6. Sign up with an admin email. Admin accounts are activated automatically. Other sign-ups wait for activation.

To inspect the interface before configuring Clerk, run `npm run dev` and open `http://localhost:5173/?demo=admin` or `http://localhost:5173/?demo=translator`.

### Demo mode

The demo is a complete, clickable copy of the app backed by memory instead of the API. It seeds five fictional translators, about five weeks of shifts, timesheets in every state (submitted, approved, rejected with an admin note, never submitted), expenses, an overnight shift that crosses Sunday midnight, and two MYOB payroll categories.

Everything works: approving, sending back, reopening, correcting times, adding and deleting shifts, activating a translator, editing names and card IDs, saving payroll categories, submitting a timesheet as a translator, and the three downloads. Changes live only in the browser tab and reset when you reload. Downloads are real files generated by the same `src/shared/export.ts` code the Worker uses, so the CSV and MYOB output you see is identical to production.

The demo loads in local development, or in any build made with `VITE_DEMO=true`. It never contacts the API or the database. Leave `VITE_DEMO` unset for a production deployment.

If you develop on Windows in a restricted sandbox, set `XDG_CONFIG_HOME` to a writable project-local directory before running Wrangler. The project `.wrangler` and `.wrangler-config` directories are ignored by Git.

## Production setup

1. Create a Cloudflare account and authenticate Wrangler locally with `npx wrangler login`.
2. Run `npx wrangler d1 create translator-roster`. Replace `REPLACE_WITH_D1_DATABASE_ID` in `wrangler.jsonc` with the returned database ID.
3. Set `VITE_CLERK_PUBLISHABLE_KEY` in the build environment. Configure Clerk for the production `workers.dev` URL or your custom domain.
4. Add Worker secrets with `npx wrangler secret put CLERK_SECRET_KEY`, `CLERK_JWT_KEY`, `ADMIN_EMAILS`, and `APP_URL`. `APP_URL` must be the exact public origin, such as `https://translator-roster.example.workers.dev`.
5. Run `npm run db:migrate:remote` and `npm run deploy`.
6. Sign in as one of the configured admins, activate translators, enter their MYOB card IDs, and set the Standard and Sunday payroll category names to exactly match MYOB.

Do not run the remote migration against an existing database without checking whether it contains live data. This repository had no local `.env` or Prisma migrations when rebuilt; no existing remote database was changed.

## Deploying changes

The live app runs at `https://timesheets.courant.live`. Cloudflare Workers Builds is connected to this repository, so every push to `main` runs `npm run build`, applies any new D1 migrations with `npx wrangler d1 migrations apply translator-roster --remote`, and runs `npx wrangler deploy`. The production `VITE_CLERK_PUBLISHABLE_KEY` is set as a build variable there; build logs are under the Worker's Settings → Build in the Cloudflare dashboard.

Test changes locally with `npm run dev` before merging. Preview builds are off on purpose: a preview would share the production database and secrets, and Clerk production only accepts `courant.live` origins.

To deploy by hand instead, pass the production key in the shell so it overrides the development key in `.env`: `VITE_CLERK_PUBLISHABLE_KEY=pk_live_… npm run deploy`. `npx wrangler rollback` restores the previous Worker version but does not undo migrations.

## Importing a roster

Admins can import a tour roster from Excel under **Roster → Import a roster**. The workbook is read in the browser; only the confirmed shifts are sent to the server.

- Any table with **Name** and **Email** header cells is read, along with optional **Role** and **Status** columns. Every other column whose header is a date (`SEP 22 SHOW`, `22/9`, `Mon 22nd September`, or a real date cell) is a show day, and each filled cell in it (`11:00 - 2330`, `9am - 5pm`, `22:00 - 2:00`) becomes a shift. An end time before the start runs past midnight. A bare `9-5` means 9am to 5pm.
- The single-cell row above a table, such as a merged `MELBOURNE` banner, names the city. The shift note becomes `Event · City · Role`. The event name defaults to the file name without words like "interpreter sheet".
- Sheets without such a table are ignored, which covers pay and profit summaries and copies without emails. Rows whose Status isn't "Confirmed" are skipped.
- Dates without a year use the year that puts them nearest today. Pick a year in the preview to override it. Times are read as Sydney time.
- The preview shows every row. The admin can untick rows, correct times, or enter times the reader couldn't understand before importing.
- People are matched by email. Someone new is added straight away as an active translator with no sign-in (`users.clerk_id` is null). When they sign up with that email, their account takes over that row and its shifts. A pending sign-up who is rostered is activated. Admin and deactivated accounts are skipped. Shifts already on the roster are skipped, so importing the same file twice is safe.

**Read with AI (beta).** If `DEEPSEEK_API_KEY` is set as a Worker secret, the preview offers a button that sends a plain-text copy of every sheet, including names and email addresses, to DeepSeek and shows the rows it returns, through the same checks and editable preview. Nothing is sent unless an admin clicks it and confirms. Set the key with `npx wrangler secret put DEEPSEEK_API_KEY`, ideally one with a low spending cap. `DEEPSEEK_MODEL` overrides the default `deepseek-chat`. Remove the secret to turn the feature off.

## MYOB exports

The **MYOB timesheets** download follows MYOB Business's documented timesheet import shape: a first row containing `{}`, a tab-separated header, employee name and card ID, payroll category, date, and decimal hours. Standard and Sunday parts of an overnight shift become separate entries. Match the two category names in the admin Export tab to your MYOB pay items. See [MYOB importing timesheets](https://www.myob.com/au/support/myob-business/import-export/importing-data/importing-timesheets).

The **expenses CSV** is a reimbursement review file, not a MYOB timesheet import. Reimbursements are handled separately in MYOB: [MYOB reimbursing an employee](https://www.myob.com/au/support/myob-business/payroll/reimbursing-an-employee). Review the expense file and receipt confirmations before paying. Import each timesheet period into MYOB only once to avoid duplicate hours.

## Checks

Run `npm test` for session-token checks, Sydney overnight, Sunday, daylight-saving and missing-timesheet calculations, the expense-week rule, the three export formats (CSV quoting, formula-injection neutralising, date filtering, the MYOB row shape and its card-ID and category rules), and error-record severity, redaction and truncation.

Run `npm run build` for TypeScript and production bundling. `npm run check:config` fails if `wrangler.jsonc` still holds the D1 placeholder, the Clerk publishable key is unset, or the local `ADMIN_EMAILS` is missing, malformed, duplicated or not exactly two addresses — that list is the whole authorisation model, so a typo there locks out the wrong person. `npm audit --cache .npm-cache` checks installed packages; the remaining advisories are all in the Wrangler/Miniflare build tooling and are not shipped in the Worker bundle.

## Behaviour notes

- A roster shift cannot be edited while its timesheet is approved; reopen the timesheet first. Deleting a shift has always been blocked once a timesheet exists.
- An admin "Correct" resets the timesheet to submitted and clears the previous reviewer and review time.
- Expense dates must fall in the Monday–Sunday week of the shift, in Sydney time, so a taxi or parking receipt dated earlier in the week is accepted but one from a different week is rejected.

## Error log

Every failure that matters is written to the `error_logs` table (migration `0002_error_logs.sql`), so an agent or a person can audit what happened without replaying a request.

- **What is logged:** every 5xx, and every 4xx except `401`, `403` and `404` — a rejected timesheet or an invalid export range is exactly the kind of thing worth auditing, while "not signed in" and "not found" are noise.
- **What a row holds:** timestamp, level (`warn`/`error`), status, method, path with query string, error name, message, stack, the acting user's id, email, role and account status, a `request_id`, and a small JSON detail blob.
- **Safety:** messages and stacks are truncated (1,000 / 4,000 characters) and bearer tokens, Clerk keys, `sk-`/`pk-`/`rk-` keys and JWTs are redacted before storage. The insert is best-effort and never blocks or changes a response.
- **Correlation:** a failed response carries `X-Request-Id` in the header and `requestId` in the body; the same value is stored on the row.
- **Reading it:** as an admin, `GET /api/admin/errors` returns the newest first.

```bash
curl -H "Authorization: Bearer $TOKEN" \
  "https://<worker>/api/admin/errors?since=2026-10-28T00:00:00Z&level=error&limit=50"
```

Query parameters: `since` (ISO timestamp), `level` (`warn` or `error`), `status` (three-digit code), `limit` (1–200, default 50). Each row is self-contained, so an agent can group by `code` + `path` and read `message`/`stack` to find the cause. `wrangler tail` also prints one JSON line per logged failure with the same `request_id` for live debugging.

**Retention.** A cron trigger (`0 3 1 * *` in `wrangler.jsonc`, first of the month at 03:00 UTC) calls the Worker's `scheduled` handler, which deletes rows older than the retention window in chunks of 500 until nothing is left to delete. The default is **90 days**; set `ERROR_LOG_RETENTION_DAYS` as a Worker secret or variable to change it (clamped to 1–3650, and a bad or missing value falls back to 90 rather than wiping the log). The prune logs one JSON line — `{"event":"error_logs_pruned","deleted":N,"cutoff":"…"}` — and never throws, so a database problem cannot fail the scheduled run.
